# ADR: Открытие депозитов онлайн (MVP)

### **Название задачи:**
Реализация MVP для открытия депозитов и накопительных счетов онлайн через интернет-банк и сайт банка «Стандарт»

### **Автор:**
Команда цифровой трансформации розничного бизнеса

### **Дата:**
2026-02-01

### **Функциональные требования**
Верхнеуровневые Use Cases для MVP открытия депозитов онлайн:

| **№** | **Действующие лица или системы** | **Use Case** | **Описание** |
| :-: | :- | :- | :- |
| UC-1 | Клиент, Интернет-банк, Сервис депозитов, АБС | Просмотр доступных депозитов в интернет-банке | 1. Клиент входит в интернет-банк. 2. Система запрашивает актуальные ставки из сервиса депозитов. 3. Сервис депозитов возвращает общие и персонализированные ставки. 4. Клиент видит список депозитов с актуальными ставками. |
| UC-2 | Клиент, Интернет-банк, Сервис депозитов, Kafka, АБС, СМС-шлюз | Подача заявки на открытие депозита через интернет-банк | 1. Клиент выбирает депозит, указывает счёт и сумму. 2. Интернет-банк отправляет СМС-код для подтверждения. 3. Клиент вводит СМС-код. 4. Заявка передаётся через Kafka в сервис депозитов. 5. Сервис депозитов создаёт заявку в АБС. 6. Клиент получает подтверждение о приёме заявки. |
| UC-3 | Менеджер бэк-офиса депозитов, АБС, Сервис депозитов, СМС-шлюз | Обработка заявки на депозит (MVP) | 1. Менеджер бэк-офиса видит новую заявку в АБС. 2. Менеджер согласовывает ставку (при необходимости запрашивает данные у отдела кредитования). 3. Менеджер подтверждает условия депозита в АБС. 4. Сервис депозитов отправляет СМС клиенту о подтверждённой ставке. 5. После открытия депозита клиент получает СМС-уведомление. |
| UC-4 | Потенциальный клиент, Сайт, Система кол-центра, Оператор кол-центра | Подача заявки на депозит через сайт | 1. Клиент заходит на сайт и видит список депозитов с актуальными ставками. 2. Клиент заполняет форму заявки (Ф.И.О., номер телефона). 3. Заявка передаётся в систему кол-центра. 4. Менеджер кол-центра связывается с клиентом и предлагает условия. 5. Клиент приходит в отделение для идентификации и оформления. |
| UC-5 | Сотрудник отдела кредитования, АБС, Сервис депозитов | Расчёт и обновление ставок по депозитам | 1. Сотрудник кредитования рассчитывает ставки на основе ставки рефинансирования ЦБ и кредитного риска. 2. Ставки загружаются в сервис депозитов (замена ручного Excel-процесса). 3. Ставки становятся доступны во всех каналах (интернет-банк, сайт). |
| UC-6 | Менеджер бэк-офиса депозитов, АБС, Сервис депозитов | Определение специальных ставок для VIP-клиентов | 1. Менеджер бэк-офиса определяет крупного клиента. 2. Запрашивает анализ кредитного риска у отдела кредитования. 3. На основе данных формирует специальную ставку. 4. Ставка сохраняется в сервисе депозитов и привязывается к клиенту. |

### **Решение**

#### Общий подход

Для реализации MVP выбрана стратегия поэтапного перехода от монолитной архитектуры интернет-банка к микросервисной — в рамках задачи открытия депозитов. Ключевое архитектурное решение — создание **отдельного сервиса депозитов** (Deposit Service), который инкапсулирует бизнес-логику работы с депозитами и выступает посредником между клиентскими каналами и АБС.

#### Ключевые решения и обоснования

1. **Сервис депозитов как отдельный микросервис.** Реализуется на Java Spring Boot — эта технология уже используется в системе кол-центра, и в команде АБС есть специалисты с опытом в Java-стеке. Сервис использует собственную БД PostgreSQL для хранения заявок и кэширования ставок, что снижает нагрузку на Oracle АБС.

2. **Apache Kafka как брокер сообщений.** Для асинхронного взаимодействия между интернет-банком и сервисом депозитов / АБС. Это решает проблему перегрузки БД АБС и обеспечивает отказоустойчивость. Поскольку текущая платформа интернет-банка (.NET Framework 4.5) несовместима с Kafka напрямую, реализуется отдельный микросервис-адаптер (.NET Core), который принимает запросы от монолита и публикует их в Kafka.

3. **API Gateway** для маршрутизации запросов между монолитом интернет-банка и новыми микросервисами. Обеспечивает единую точку входа, SSL-терминацию, балансировку нагрузки.

4. **Интеграция с АБС через API-слой**, а не напрямую с БД Oracle. Команда АБС разрабатывает REST API поверх существующих PL-SQL процедур для безопасного доступа к данным.

5. **Сервис уведомлений** — отдельный микросервис для отправки СМС через существующий СМС-шлюз. Подписывается на события из Kafka (подтверждение ставки, открытие депозита) и отправляет уведомления.

6. **Интеграция сайта с системой кол-центра.** Заявки с сайта передаются в систему кол-центра через её существующий API (Java Spring Boot). Актуальные ставки для отображения на сайте берутся из сервиса депозитов через API.

### **Альтернативы**

1. **Доработка монолита интернет-банка без микросервисов.** Можно было бы добавить функционал депозитов в существующий монолит ASP.NET MVC. Плюсы: проще реализовать, меньше интеграционных точек. Минусы: усиление зависимости от подрядчика ядра, невозможность независимого масштабирования, усложнение кодовой базы, несовместимость с Kafka.

2. **Прямая интеграция интернет-банка с API АБС (синхронная).** Плюсы: проще в реализации, реальное время. Минусы: АБС может не выдержать нагрузку, SPOF (Single Point of Failure), вертикальное масштабирование Oracle дорого.

3. **Полная замена интернет-банка на новую платформу.** Плюсы: современный стек, отсутствие legacy-ограничений. Минусы: огромные сроки и бюджет, высокие риски, выходит за рамки MVP.

4. **Использование RabbitMQ вместо Kafka.** Плюсы: проще в настройке, хорошо работает для point-to-point. Минусы: не соответствует требованию бизнеса использовать Kafka «на перспективу», менее масштабируемый для будущих сценариев.

### **Недостатки, ограничения, риски**

**Недостатки:**
- Усложнение инфраструктуры: добавление Kafka, новых микросервисов, API Gateway увеличивает операционную сложность.
- Необходимость поддержки двух архитектурных подходов одновременно (монолит + микросервисы) в переходный период.
- Eventual consistency: асинхронное взаимодействие через Kafka означает, что данные в интернет-банке и АБС могут быть временно несогласованными.

**Ограничения:**
- АБС масштабируется только вертикально — это bottleneck для будущего роста.
- Текущая платформа интернет-банка (.NET Framework 4.5) не поддерживает Kafka напрямую — необходим адаптер.
- MVP требует ручной обработки заявок бэк-офисом — не полная автоматизация.
- Новые клиенты с сайта всё ещё должны приходить в отделение для идентификации.

**Риски:**
- **Технический риск:** Интеграция Kafka с legacy-системами может оказаться сложнее, чем ожидается.
- **Организационный риск:** Необходимо координировать работу нескольких команд (интернет-банк, АБС, кол-центр, подрядчик).
- **Риск производительности:** При росте числа заявок АБС может стать узким местом даже при асинхронном взаимодействии.
- **Риск зависимости от подрядчика:** Несмотря на минимизацию, некоторые изменения в ядре интернет-банка могут потребовать участия подрядчика.
- **Риск безопасности:** Новые интеграционные точки расширяют поверхность атаки — необходим аудит безопасности.
