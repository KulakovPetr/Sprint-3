# ADR: Передача ставок по депозитам в кол-центр и партнёрский кол-центр

### **Название задачи:**
Обеспечение доступа операторов кол-центра и партнёрского кол-центра к актуальным ставкам по депозитам банка «Стандарт»

### **Автор:**
Команда цифровой трансформации розничного бизнеса

### **Дата:**
2026-02-01

| UC-1 | Оператор кол-центра, Система кол-центра, Сервис депозитов | Консультирование клиента по ставкам депозитов | 1. Клиент звонит в кол-центр. 2. Оператор открывает раздел «Ставки по депозитам» в системе кол-центра. 3. Система кол-центра запрашивает актуальные ставки через API сервиса депозитов. 4. ### **Нефункциональные требования**

| **№** | **Требование** |
| :-: | :- |
| NFR-1 | Ставки должны обновляться в системе кол-центра в реальном времени (не более 1 минуты задержки) |
| NFR-2 | Файлы со ставками для партнёрского кол-центра генерируются автоматически при каждом обновлении |
| NFR-3 | SFTP-соединение должно быть защищено (SSH-ключи, шифрование) |
| NFR-4 | Формат файлов для SFTP — CSV с UTF-8 кодировкой (совместимость с партнёрской системой) |
| NFR-5 | Доступность API ставок — 99,9% (SLA) |
| NFR-6 | Система должна работать в рамках существующей инфраструктуры (Kafka, Java Spring Boot) |
| NFR-7 | Партнёрский кол-центр забирает файлы самостоятельно — push-модель не требуется |
| NFR-8 | Логирование всех операций передачи ставок для аудита |

### **Решение**

#### Общий подход

Решение основывается на архитектуре MVP (ADR из Task3) и расширяет сервис депозитов (Deposit Service) двумя новыми интеграционными каналами:

1. **API для системы кол-центра** — синхронный REST API + event-driven обновление через Kafka.
2. **SFTP-экспорт для партнёрского кол-центра** — автоматическая генерация файлов со ставками и размещение на SFTP-сервере банка.

#### Ключевые решения и обоснования

1. **Event-driven синхронизация ставок с кол-центром через Kafka.** Система кол-центра уже построена на микросервисной архитектуре (Java Spring Boot) и может быть расширена новым микросервисом-подписчиком, который слушает топик `deposit-rates` в Kafka. Это обеспечивает минимальную задержку и не создаёт нагрузки на сервис депозитов при каждом запросе оператора.

2. **REST API сервиса депозитов как fallback.** В дополнение к event-driven модели, система кол-центра может запрашивать ставки напрямую через REST API сервиса депозитов. Это обеспечивает надёжность — если событие не было получено, данные можно получить синхронно.

3. **SFTP-сервер для партнёрского кол-центра.** Партнёр не может принимать API-вызовы. Решение — разместить SFTP-сервер в DMZ банка. Компонент Deposit Service при каждом обновлении ставок генерирует CSV-файл и загружает его на SFTP. Партнёрский кол-центр забирает файл по расписанию.

4. **Формат данных.** CSV выбран как универсальный формат, понятный любой системе. Файл содержит: тип депозита, срок, ставка, дата обновления, условия.

5. **Расширение системы кол-центра.** Новый микросервис `rates-consumer` добавляется в систему кол-центра. Разработку могут выполнить специалисты из команды АБС, имеющие опыт в Java-стеке, совместно с командой подрядчика кол-центра.

### **Альтернативы**

1. **Прямой API-вызов из системы кол-центра к АБС.** Плюсы: без посредника. Минусы: перегрузка АБС, отсутствие кэширования, нарушение архитектурного принципа изоляции АБС.

2. **Отправка файлов по email партнёрскому кол-центру.** Плюсы: простота. Минусы: ненадёжно, ручной процесс, нет автоматизации, проблемы с безопасностью.

3. **Развёртывание API-шлюза для партнёрского кол-центра.** Плюсы: реальное время, двусторонняя интеграция. Минусы: партнёр не готов принимать API-вызовы, потребуются доработки на стороне партнёра.

4. **Публикация ставок на внешнем веб-портале.** Плюсы: доступность для партнёра без SFTP. Минусы: вопросы безопасности, нужна аутентификация, дополнительная система.

### **Недостатки, ограничения, риски**

**Недостатки:**
- SFTP-обмен не обеспечивает обновление ставок в реальном времени для партнёрского кол-центра — есть задержка (зависит от периодичности забора файлов партнёром).
- Необходимость поддержки двух моделей интеграции (API + SFTP) увеличивает операционную сложность.
- CSV-формат не поддерживает сложную структуру данных (например, вложенные условия по депозитам).

**Ограничения:**
- Партнёрский кол-центр может забирать файлы только по SFTP — другие протоколы не поддерживаются.
- Обновление ставок зависит от ручного процесса расчёта отделом кредитования (в будущем планируется автоматизация).
- Объём данных по ставкам невелик, но при расширении линейки продуктов формат файла может потребовать пересмотра.

**Риски:**
- **Рассинхронизация данных:** Если Kafka-событие потеряется, операторы кол-центра могут видеть устаревшие ставки. Митигация: REST API fallback + мониторинг.
- **Безопасность SFTP:** Утечка файлов со ставками через компрометацию SFTP. Митигация: SSH-ключи, IP-фильтрация, ротация ключей.
- **Перегрузка кол-центра:** При маркетинговой кампании количество звонков может превысить возможности. Митигация: подключение партнёрского кол-центра, IVR-система.
- **Зависимость от партнёра:** Если партнёр не забирает файлы регулярно, его операторы консультируют по устаревшим ставкам. Митигация: мониторинг, SLA с партнёром.
