# FURPS+ Требования — Цифровая трансформация банка «Стандарт»

## Открытие депозитов и накопительных счетов онлайн (MVP)

| Код | Требования                         | Комментарий  |
|-----|------------------------------------|--------------|
| F   | **Функциональные (Functionality)** |              |
|     | На сайте новый клиент видит список доступных депозитов с актуальными ставками | Ставки обновляются ежедневно на основе ставки рефинансирования ЦБ |
|     | Клиент может подать заявку на депозит на сайте, оставив номер телефона и Ф.И.О. | Заявка попадает в систему кол-центра для обработки менеджером |
|     | Менеджер кол-центра видит заявку в системе кол-центра и связывается с клиентом для предложения условий | Менеджер может предложить особые условия |
|     | В интернет-банке клиент видит список доступных депозитов с актуальными и персонализированными ставками | Персонализированные ставки рассчитываются на основе данных клиента |
|     | Клиент может подать заявку на открытие депозита в интернет-банке, указав счёт и сумму | Основной сценарий MVP |
|     | Подтверждение операции открытия депозита через СМС-код | Функционал СМС реализован в ядре, но лучше реализовать силами банка без доработки подрядчика |
|     | Бэк-офис обрабатывает заявки на депозит в АБС (MVP) | В MVP заявку подтверждает менеджер бэк-офиса вручную |
|     | Клиент получает СМС-уведомление после подтверждения размера ставки | Через СМС-шлюз → телеком-оператор |
|     | Клиент получает СМС-уведомление после открытия депозита | Через СМС-шлюз → телеком-оператор |
|     | Систематизация управления ставками по депозитам (перенос из XLS-файлов) | Сейчас ставки ведутся только в Excel, нужна автоматизация. Возможно, стоит реализовать в АБС |
|     | Процесс согласования ставки по заявке автоматизирован в АБС | Сотрудники депозитов и кредитов работают с данными раздельно |
|     | Новые клиенты с сайта направляются в отделение для идентификации | Требование законодательства — банки не могут принимать новых клиентов без личной проверки |
| U   | **Удобство использования (Usability)** |              |
|     | Максимально удобный интерфейс работы для клиента | Бизнес-требование — удобство = конкурентное преимущество для привлечения молодых клиентов |
|     | Соблюдение корпоративной системы дизайна | Привычные цвета и брендированные элементы |
|     | Единообразие UX между сайтом и интернет-банком | Важно для целостного восприятия бренда |
|     | Интуитивно понятный процесс подачи заявки на депозит | Минимальное количество шагов для целевой аудитории (молодые клиенты) |
| R   | **Надёжность (Reliability)** |              |
|     | Все сервисы должны работать 24/7 с доступностью 99,9% | SLA = 99.9% (не более ~8.7 часов простоя в год) |
|     | В случае сбоя в основном ЦОД — переключение на резервный ЦОД | У банка есть резервный ЦОД |
|     | Сервисы интернет-банка должны оставаться доступными при сбоях в ЦОД | Критично для онлайн-обслуживания |
|     | Избежать прямой работы интернет-банка с API АБС в новом процессе | БД АБС перегружена, прямое взаимодействие создаёт риски для основной банковской системы |
|     | Обеспечить отказоустойчивость при онлайн-подаче заявок | Большое количество заявок не должно ставить под угрозу работоспособность банка |
| P   | **Производительность (Performance)** |              |
|     | Отклик по всем операциям — миллисекунды | Бизнес-требование |
|     | Исправить проблему с загрузкой справочных данных (сейчас > 1 сек) | Текущая проблема с платёжными справочниками — нужно кэширование |
|     | Горизонтальное масштабирование и распределение запросов между серверами и ЦОД | Для обеспечения нагрузки при росте клиентской базы |
|     | Учесть, что АБС масштабируется только вертикально | Ограничение архитектуры Oracle + PL-SQL |
|     | Равномерное распределение нагрузки (load balancing) | Между серверами, приложениями и ЦОД |
| S   | **Поддерживаемость (Supportability)** |              |
|     | Разработка документации для дальнейшего расширения системы | Для будущих продуктов (кредиты и др.) |
|     | Перевод интернет-банка на микросервисную архитектуру (в рамках задачи депозитов) | Поэтапная миграция от монолита |
|     | Возможность расширения без доработки ядра интернет-банка подрядчиком | Минимизация зависимости от подрядчика |
|     | Использование стандартных API и протоколов для интеграции | Для расширяемости и совместимости |
| +R  | **+ Ограничения (Restrictions)** |              |
|     | Максимально использовать технологии, которые есть в банке (MS SQL, Oracle) | Минимизация рисков и затрат на обучение |
|     | Новые технологии должны быть совместимы с существующими платформами | .NET, Java, Delphi/PL-SQL |
|     | Внутри банка должна быть экспертиза в новых технологиях (хотя бы на уровне языков) | У команды АБС есть опыт в Java-стеке |
|     | Kafka для очередей сообщений (на перспективу) | Текущая версия интернет-банка несовместима — требуется миграция |
|     | Шифрование трафика (TLS/HTTPS) для сайта и интернет-банка | Передаётся чувствительная информация клиентов |
|     | Разделение доступа: сотрудники депозитов и кредитов не имеют доступа к данным друг друга | Требование безопасности |
|     | Не использовать прямую интеграцию интернет-банка с БД АБС для новых процессов | Текущая прямая интеграция — антипаттерн, БД перегружена |
|     | Минимизировать доработки ядра интернет-банка подрядчиком | Зависимость от подрядчика — риск для сроков и бюджета |
|     | Реализацию бизнес-функционала СМС вести силами команды банка | Избежать доработки ядра подрядчиком |
